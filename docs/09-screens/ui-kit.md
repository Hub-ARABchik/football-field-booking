# UI Kit — FFBS (Football Field Booking System)

**Назначение:** единая визуальная система веб-платформы поиска и бронирования футбольных площадок.  
**Версия:** 1.0 · **Статус:** проектирование UI/UX  
**Основной сценарий:** найти площадку в Худжанде, проверить свободное время и отправить заявку.

> Структура документа ориентирована на пример UI-kit EDMS, но цветовая система, компоненты и сценарии переработаны для FFBS.

## 1. Принципы интерфейса

FFBS объединяет клиентов и независимых владельцев футбольных площадок. Пользователь должен быстро сравнить объекты, увидеть доступное время и понять статус заявки.

- **Площадка и время — в приоритете:** фотографии, адрес, цена за час и доступные слоты важнее второстепенных сведений.
- **Понятный путь к бронированию:** от каталога до отправки заявки без лишних шагов.
- **Разделение ролей:** отдельная навигация для CUSTOMER, OWNER и ADMIN.
- **Понятные статусы:** подпись всегда сопровождает цвет.
- **Локальный контекст:** Худжанд, сомони (TJS), часовой пояс Asia/Dushanbe.
- **Локализация:** предусмотреть русский и таджикский языки (RU / TJ).

## 2. Сетка и адаптивность

### Desktop — 1440 px
- 12 колонок, Center.
- Контентная область — 1320 px; ширина колонки — 88 px.
- Межколонник — 24 px; внешние поля — 60 px.

### Tablet — 768 px
- 12 колонок, внешние поля — 24 px, межколонник — 16–24 px.

- Карточки располагаются по две в ряд, если хватает ширины.

- Основные действия доступны без горизонтальной прокрутки.
- Календарь и временные слоты используют компактную сетку.
- Таблицы кабинетов превращаются в карточки или адаптивные списки.

## 5. Компоненты и состояния

### Button
Варианты: `Primary`, `Secondary`, `Outline`, `Danger`.  
Состояния: `Default`, `Hover`, `Focus`, `Disabled`, `Loading`.

- Высота — 48 px на desktop и не менее 44 px на мобильных устройствах.
- Главный сценарий экрана выделяется одной доминирующей Primary-кнопкой.
- Формулировки действий: «Найти площадку», «Отправить заявку», «Подтвердить», «Добавить площадку».
- Удаление площадки и отмена бронирования не оформляются как Primary-действие.

### Input / Select / Date Picker
Состояния: `Default`, `Focus`, `Error`, `Disabled`.

- У каждого поля есть видимый label; placeholder не заменяет подпись.
- Ошибка сопровождается поясняющим текстом.
- Дата — например, `20.11.2026`; время — `18:00–19:00`.
- Цена всегда содержит единицу: «120 сомони / час».

### Badge / Status

| Системное значение | Подпись в интерфейсе | Тип |
|---|---|---|
| `PENDING` | Ожидает подтверждения | Warning |
| `CONFIRMED` | Подтверждено | Success |
| `CANCELLED` | Отменено | Neutral / Danger |
| `REJECTED` | Отклонено | Danger |
| `COMPLETED` | Завершено | Neutral / Success |

### Состояния временного слота

| Состояние | Подпись | Поведение |
|---|---|---|
| Available | Свободно | доступен для выбора |
| Selected | Выбрано | акцентная заливка и контур |
| Occupied | Занято | недоступно для выбора |
| Disabled | Недоступно | отключённое состояние |
| Past | Прошло | приглушённое состояние |

### Field Card
Карточка поля содержит фотографию, название, адрес/район, размер (5×5, 7×7 и т. п.), тип покрытия, удобства, цену за час и действие «Подробнее» или «Выбрать время». Карточки используют Auto Layout и корректно расширяются при длинных названиях.

### Booking Card / Booking Row
Отображает площадку, клиента, дату, интервал, стоимость и статус. Владелец видит действия «Подтвердить» и «Отклонить» для ожидающих заявок. Клиент видит детали и действие отмены, если оно разрешено правилами системы.

### Calendar & Time Slot
- Календарь различает доступные и недоступные даты.
- Временные интервалы — отдельные кнопки одинаковой высоты.
- Выбранный слот нельзя спутать с занятым или отключённым.
- После отправки заявки показывается сообщение об успешной отправке и статус «Ожидает подтверждения».
- Интерфейс не обещает мгновенное подтверждение, если решение принимает владелец.

### Modal / Confirmation Dialog
Используется для отмены заявки, удаления площадки и отклонения бронирования. Диалог объясняет последствие и предлагает безопасную отмену действия.

## 6. Навигация по ролям

**Публичная:** Площадки, Как это работает, Владельцам, RU / TJ, Войти / Профиль.

**Клиент:** Обзор, Мои бронирования, Избранное (если реализовано), Профиль.

**Владелец:** Обзор, Мои площадки, Бронирования, Расписание, Настройки.

**Администратор:** Обзор, Пользователи, Площадки, Бронирования, Модерация.

Разделы, функциональность которых ещё не реализована, не должны выглядеть как доступные рабочие функции.

## 8. Визуальные материалы

- Использовать реалистичные фотографии футбольных полей: искусственный газон, ворота, разметка, освещение, крытые и открытые площадки.
- Сохранять единый стиль освещения и кадрирования изображений.
- Не использовать изображения товаров, документов, офисов или бизнес-иллюстрации, не связанные со спортом.
- Не показывать оплату картой как действующую функцию, если платёжный провайдер не подключён.
- Демонстрационные названия и цены маркировать как примеры, если они не подтверждены реальным каталогом.

## 10. Согласование с моделью данных

- Новое бронирование отображается как заявка со статусом `PENDING`.
- После решения владельца статус обновляется.
- Свободное время проверяется сервером; UI-состояние слота не заменяет серверную проверку.
- Один временной интервал площадки нельзя выдать двум активным бронированиям.
- Платёжный интерфейс не должен изображать онлайн-оплату как реализованную функцию, пока не подключён провайдер.

**Замечание по актуальности схемы:** корневой `database.sql` содержит упрощённую старую модель с ролями `client/admin`, без полноценной связи площадки с владельцем и без статуса `REJECTED` у бронирования. Более поздний `docs/08-technical-specification.md` описывает целевую модель `CUSTOMER/OWNER/ADMIN` и статус `REJECTED`. Перед интеграцией кабинета владельца и сценария отклонения необходимо синхронизировать SQL-схему с техническим заданием. Дизайн ориентируется на целевую модель из технического задания.
